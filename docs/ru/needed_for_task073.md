# Что ещё нужно для TASK-073

Русское зеркало. [Английский источник](../needed_for_task073.md).

Этот документ перечисляет всё, чего ещё не хватает TASK-073 (GPU acceptance
harness, см. [PROJECT_ROADMAP.md](PROJECT_ROADMAP.md)), почему каждый пункт
важен для шлюза G3 и что именно оператор должен предоставить, решить или
сделать, чтобы агент мог завершить задачу. Документ описывает `main` на коммите
`4dcae07` (2026-10-21) и работу на RTX 4050 в ветке `task-073-render-profile`.

## 1. Текущее состояние задачи

### 1.1 Существуют две реализации

* **В `main` (работа на Mac/Cursor, коммит `4dcae07`):** `?g3=1` выбирает
  production-сцену измерения (`apps/web/src/render/g3-mode.ts`,
  `apps/web/src/render/g3-passes.ts`): установленная FPV-камера, ремаппинг
  «рыбьего глаза», аналоговое видео и синтетическая LWIR-камера, только WebGL2.
  `scripts/check-gpu-perf.mjs` измеряет её на однотайловой CC0-фикстуре
  (`tests/fixtures/tiles/`) и оценивает через `scripts/gpu-trace.mjs` и
  `scripts/bench-render.mjs`. Оператор принял пределы 60 FPS
  **медиана <= 16.680 мс и p99 <= 17.665 мс** и панель 59.88 Гц; предел
  120 FPS остаётся **p99 <= 8.33 мс**. DoD дополнительно требует, чтобы
  изображение полёта заполняло активный физический дисплей.
* **В ветке `task-073-render-profile` (коммит `bf53d57`, не слита):**
  `?profile=full` (`apps/web/src/render/sensor-views.ts`) рендерит ту же цепочку
  камер в виде вставок, `scripts/generate-render-tileset.mjs` создаёт
  детерминированный синтетический CC0-ландшафт нагрузки (8 км, 341 тайл),
  `scripts/capture-render.mjs` выполняет полноэкранный захват и снимает память
  GPU-процесса браузера через счётчики Windows. Локальный, не зафиксированный
  `scripts/diagnose-render.mjs` определяет причины опоздавших кадров с помощью
  таймерных запросов GPU WebGL2. Эта ветка меняет `apps/web/src/FlightScene.tsx`,
  `apps/web/package.json`, roadmap и другие файлы, которые также изменил
  `4dcae07`, поэтому без конфликтов не сливается.

проходит.

## 2. Недостающие пункты и как их предоставить

Для каждого пункта указано, чего не хватает, почему это важно для G3, что
оператор предоставляет или решает и что затем делает агент. **Работа агента**
требует только согласия.

### 2.1 Один harness вместо двух

* **Не хватает:** единого пути измерения. `?g3=1` и `?profile=full`
  пересекаются.
* **Оператор решает:** какой остаётся. Рекомендуется: оставить в `main` `?g3=1`
  и `scripts/check-gpu-perf.mjs` единственным harness и перенести из ветки то,
  чего в `main` нет: генератор тайлсета нагрузки, полноэкранный режим на
  физическом дисплее, сбор памяти GPU-процесса в Windows, запись частот через
  `nvidia-smi` и скрипт диагностики. Затем убрать `?profile=full`.
* **Затем агент (работа агента):** переносит эти части в `main` через новую
  ветку, повторяет тесты и проверки документации и удаляет или закрывает
  `task-073-render-profile`.

### 2.2 Правило разрешения против «заполнения дисплея»

* **Не хватает:** профиля, который принимают оба правила. `assessGpu` принимает
  только 1920 x 1080 при DPR 1, а DoD требует, чтобы изображение полёта
  заполняло активный физический дисплей. Рабочий стол M4 — 2560 x 1440 (родная
  панель 2560 x 1664, Retina DPR 2), поэтому полноэкранное изображение там не
  является 1920 x 1080 DPR 1. На RTX 4050 внешний дисплей 1920 x 1080, но canvas
  полёта по-прежнему занимает лишь часть разметки приложения.
* **Оператор выбирает один из вариантов:**
  1. **Сохранить 1920 x 1080 DPR 1** и предоставить для каждого устройства
     дисплей ровно 1920 x 1080 с масштабом 1x (внешний монитор 1920 x 1080 для
     Mac; имеющийся внешний монитор для RTX 4050); или
  2. **Изменить контракт** так, чтобы разрешением профиля были родные
     разрешение и DPR дисплея (документированное версионированное изменение
     анализатора и матрицы на обоих языках; пределы времени кадра не меняются).
* **Затем агент (работа агента):** делает так, чтобы измеряемый canvas полёта
  покрывал весь дисплей в режиме измерения (без боковых панелей), записывает в
  свидетельства снимок всего дисплея и размер буфера отрисовки и реализует
  вариант 2, если он выбран.

### 2.3 Время кадра RTX 4050 и настройки питания

* **Не хватает:** захвата на RTX 4050, укладывающегося в медиану <= 16.680 мс и
  p99 <= 17.665 мс при действительно повышенной частоте GPU.
* **Уже опробовано:** настройка NVIDIA для программы, режим Windows
  «Максимальная производительность» и профиль производителя Performance
  (раздел 1.2). GPU так и не вышел за пределы P5, а драйвер продолжал сообщать
  «GPU idle», поэтому эта настройка не является рычагом.
* **Оператор предоставляет далее:** это системные настройки, которые агент не
  меняет.
  1. Панель управления NVIDIA → Управление параметрами 3D → **Глобальные
     параметры** → Режим управления электропитанием → **Предпочтителен режим
     максимальной производительности** (в дополнение к записи `chrome.exe`).
  2. Если GPU всё равно остаётся в P5 или ниже: переключить ноутбук в режим
     **только дискретного GPU / MUX «Ultimate»** (ASUS Armoury Crate → GPU
     Mode), перезагрузить и проверить в параметрах дисплея Windows, какой
     адаптер управляет измеряемым дисплеем. Это убирает путь гибридной графики
     Windows, который сейчас считает нагрузку простоем.
  3. Сообщить агенту, что из этого сделано.
* **Затем агент:** повторяет 10-минутный захват и диагностику с записью частот,
  хранит каждую конфигурацию питания как отдельное свидетельство и сообщает все
  результаты. Пределы не меняются.

### 2.4 Дисплеи 120 Гц и выше

* **Не хватает:** обоих профилей 120 FPS (p99 <= 8.33 мс).
* **RTX 4050:** внешний монитор работает на 60 Гц; встроенная панель 144 Гц
  подключена к встроенному GPU Intel, поэтому не измеряет путь вывода NVIDIA в
  чистом виде. **Оператор предоставляет один из вариантов:** режим только
  дискретного GPU / MUX «Ultimate» (ASUS Armoury Crate → GPU Mode, перезагрузка,
  подтвердить, что панель работает через адаптер NVIDIA на 144 Гц) или внешний
  монитор не менее 120 Гц на порту, подключённом к GPU NVIDIA, с режимом
  1920 x 1080 при 120/144 Гц.
* **M4:** панель MacBook Air обновляется с частотой 59.88 Гц и не может
  выполнить профиль 120 FPS. **Оператор предоставляет:** внешний монитор не
  менее 120 Гц, подключённый к Mac (1920 x 1080, если в разделе 2.2 выбран
  вариант 1).
* **Затем агент:** запускает `--fps 120` на каждом устройстве.

### 2.5 Ландшафт: настоящие данные вместо фикстур

* **Не хватает:** реалистичного ландшафта. `main` измеряет на однотайловой
  CC0-фикстуре (10 092 байта резидентности тайлов на M4); тайлсет нагрузки из
  ветки — это 341 синтетический тайл без текстур (12.5 МиБ). Ни один из них не
  нагружает бюджеты 2 ГиБ / 512 МиБ и не является настоящей землёй.
* **Оператор предоставляет один из вариантов:**
  1. **Google Photorealistic 3D Tiles** через прокси TASK-063
     (`services/tiles-worker/`): проект Google Cloud с биллингом и включённым
     **Map Tiles API**, API-ключ, ограниченный этим API, аккаунт Cloudflare и
     явное разрешение на развёртывание Worker, а также настройку разрешённого
     origin и сессий. Оператор хранит ключ **только** как секрет Worker
     (`wrangler secret put`); ключ никогда не попадает в чат, репозиторий, URL
     или журналы. Ограничения политики сохраняются: только использование в
     памяти, TTL 0, без предзагрузки, без офлайн-копий, без хранения в R2 (см.
     [terrain-licensing.md](terrain-licensing.md)).
  2. **Лицензированный или собственный набор 3D Tiles** (собственная
     фотограмметрия, коммерческий набор или экспорт, лицензия которого разрешает
     локальное использование): каталог тайлсета вне репозитория, документ
     лицензии, точная строка атрибуции, начало координат
     (`latDeg,lonDeg,ellipsoidalHeightM`) и SHA-256 свидетельства лицензии.
  3. **Модель рельефа:** тайлы DEM GeoTIFF для района (например, Copernicus
     GLO-30) с URL источника и лицензией; агент пишет конвертер DEM в 3D Tiles
     (**работа агента**).
* **Также нужно:** **район работ** (координаты центра и радиус), желательно
  внутри поддерживаемого покрытия Израиля.

### 2.6 Карты: слои земного покрова и OpenStreetMap

* **Не хватает:** три тайла ESA WorldCover 2021 v200 по Израилю зафиксированы и
  декодируются (TASK-069), но не подключены к сцене; выгрузки OpenStreetMap нет;
  runtime `DataManifest` не зарегистрирован.
* **Почему:** без классов материалов излучательная способность и свойства
  поверхности в тепловизоре не могут меняться вместе с землёй.
* **Оператор предоставляет:** выгрузку OSM, скачанную оператором (например,
  Geofabrik `israel-and-palestine-latest.osm.pbf`, ODbL), с датой скачивания и
  SHA-256, хранящуюся вне репозитория, если фиксация не разрешена;
  подтверждение, что район работ лежит внутри имеющихся тайлов WorldCover
  (`N27E033`, `N30E033`, `N33E033`), либо дополнительные тайлы по процедуре
  [worldcover-data.md](worldcover-data.md).
* **Затем агент (работа агента):** регистрирует `DataManifest`, накладывает
  классы WorldCover/OSM на ландшафт и передаёт зависящие от класса
  излучательную способность и тепловые параметры в G-буфер тепловизора.

### 2.7 Тепловизор: физические температуры и настоящий прибор

* **Не хватает:**
  * **работа агента:** обе реализации используют синтетические температуры
    (`main`: `290 K + 18 K * clamp(1 - d / 80 m)` по расстоянию; ветка:
    `291 K + 14 K * max(0, n . sun)`). Тепловой баланс TASK-070
    (`ThermalField`, эфемериды Солнца, тени) и затвор/NUC TASK-072 не связаны с
    отрисовываемой сценой;
  * **данные оператора:** есть только профиль `synthetic-lwir-640`; измеренного
    прибора нет, поэтому заявлять паритет с CADEX или другим прибором нельзя.
* **Оператор предоставляет (для измеренного профиля):** модель камеры и паспорт
  (разрешение, диапазон, NETD, частота кадров, горизонтальное поле зрения
  объектива, радиометрическая или нет); сырые кадры до палитры чёрного тела или
  эталонной пластины при нескольких известных температурах (например, шагом
  10 °C от 0 до 60 °C) с температурой окружающей среды; парные записи реальных
  сцен со временем, местом и погодой (температура воздуха, влажность, ветер,
  облачность); известные значения излучательной способности местных
  материалов; хеши файлов и разрешение на их хранение.
* **Затем агент:** строит измеренный `InstrumentProfile` с хешем данных
  калибровки, связывает решатель TASK-070 с материалами ландшафта и включает
  затвор/NUC в сцене измерения.

### 2.8 WebGL2 и WebGPU

* **Не хватает:** проходы «рыбьего глаза», аналогового видео и тепловизора
  реализованы как WebGL `ShaderMaterial`; `scripts/check-gpu-perf.mjs --backend webgpu`
  завершается с `BLOCKED_EXTERNAL`.
* **Оператор решает:** требует ли G3 полнофункциональных захватов WebGPU
  (`docs/benchmarks/render-matrix.json` перечисляет оба бэкенда) или WebGL2
  принимается как production-бэкенд.
* **Затем агент (работа агента, если требуется):** переносит проходы на
  node-материалы three.js (TSL/WGSL), добавляет тесты с CPU-оракулом на
  настоящем WebGPU-оборудовании (программный Chromium пропускает WebGPU) и
  снимает WebGPU на обоих устройствах.

### 2.9 Полёт во время захвата

* **Не хватает:** аппарат стоит на земле, поэтому подгрузка ландшафта в
  движении и смена LOD не проверяются.
* **Оператор выбирает один из вариантов:** **сценарный полёт** (работа агента:
  детерминированный путь виртуального геймпада — взлёт, круг на фиксированной
  высоте и скорости, посадка — записанный как инструментирование) или **ручной
  полёт** с передатчиком в течение 11 минут.

### 2.10 Измерение памяти GPU

* **Не хватает:** согласованного источника данных о резидентности. `main`
  сообщает оценку кеша тайлсета; ветка дополнительно снимает счётчики Windows
  `GPU Process Memory` (верхняя граница для всего GPU-процесса браузера). Для
  macOS в harness нет аналогичного счётчика по процессам.
* **Оператор решает:** допустима ли на macOS оценка на стороне приложения или
  там требуется измерение средствами ОС.
* **Затем агент (работа агента):** записывает оба источника там, где они
  доступны, и указывает, какой из них использует шлюз.

### 2.11 Измерение по времени вывода на экран

* **Не хватает:** независимого измерения времени на стороне дисплея. Метки
  времени requestAnimationFrame на связке Windows/D3D11 дрожат примерно на
  ±2 мс даже для демосцены. Это лишь добавляет свидетельства и не меняет
  анализатор или его пределы.
* **Оператор предоставляет:** в Windows — разрешение скачать и запустить Intel
  PresentMon (подписанный релиз с GitHub) или установить его самому и сообщить
  путь; в macOS — Xcode Instruments (Metal System Trace), если там нужно время
  вывода на дисплей.
* **Затем агент:** записывает интервалы смены изображения на дисплее рядом с
  захватом и сообщает оба распределения.

### 2.12 Порядок в репозитории

* **Оператор решает:** что делать с `task-073-render-profile` (см. 2.1),
  фиксировать ли `scripts/diagnose-render.mjs` и добавлять ли принудительно
  свидетельства `test-results/render/` и `test-results/m4` (игнорируются
  `.gitignore`).
* На ноутбуке с RTX 4050 в Git не настроена личность пользователя; агент
  фиксирует изменения с личностью из существующей истории,
  `djdanou-cloud <djdanou@gmail.com>`, для каждой команды отдельно. Чтобы это
  изменить, задайте `git config user.name/user.email`.

## 4. Правила, которые остаются в силе

* Никогда не вставлять API-ключи, токены или пароли в чат, URL, репозиторий или
  журналы; секреты оператор помещает в хранилище секретов развёртывания.
* Пределы G3 меняет только оператор, явным записанным решением (как
  2026-10-21). Агент никогда не ослабляет пределы, предел догоняющих шагов или
  анализатор ради прохождения захвата; непрошедшие захваты остаются записанными
  как FAIL.
* Синтетические данные остаются помеченными как синтетические; классы
  поверхности не являются температурами; паритета с CADEX без измеренных данных
  нет.
* Программные или безголовые GPU никогда не подтверждают аппаратные шлюзы;
  отсутствующие устройства остаются `BLOCKED_EXTERNAL`.
